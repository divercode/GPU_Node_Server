# 第三件专利可选提纲

## 一种容器化GPU集群统一身份认证与对象级数据范围控制方法

> 仅作为第三件专利的技术交底提纲，不建议与“故障隔离”“告警联动”合并申请；是否申请需先做检索和创造性评估。

## 1. 技术问题

GPU 平台常把 OOD、Dex、FreeIPA、Nginx、后端、前端拆成多个组件。现有做法容易把身份认证只放在前端，或后端只做角色判断而不做对象级数据范围校验，导致：

- 普通用户可通过直接调用 API 越权查看他人作业/用量；
- 前端菜单隐藏被误当作授权；
- 多组件身份头被伪造；
- 写接口缺少 CSRF 防护。

## 2. 技术方案要点

1. 浏览器只访问统一 8080 入口；
2. 网关完成 OIDC 会话校验，并向 API 注入用户、邮箱、组身份头和共享密钥；
3. 后端只信任带共享密钥的代理请求，按组映射角色；
4. 后端对每个对象做数据范围校验：本人 uid、本组 account、全局角色；
5. 前端只根据 `/api/v1/me` 做菜单展示，不作为授权依据；
6. 写接口使用 HttpOnly CSRF cookie + `X-CSRF-Token` 双提交，并校验同源 Origin；
7. 所有拒绝和写操作记录 request_id/审计。

## 3. 可写的独立权利要求方向

- 一种 GPU 平台身份代理与数据范围控制方法：网关 OIDC 会话 + 身份头 + 共享密钥 + 后端对象级校验 + CSRF；
- 一种多租户 GPU 平台的作业/用量数据范围控制方法：uid/account/global 三级范围。

## 4. 风险

OIDC 反向代理、RBAC、CSRF 都是成熟技术，单独申请创造性可能不足。建议只在有**特定技术效果**时申请，例如：

- 代理头与后端缓存的组—账户—对象映射的特定校验顺序；
- 跨 OOD/平台 SPA/API 的会话与数据范围一致性机制；
- 容器多副本下的 CSRF 与会话撤销机制。

## 5. 结论

优先申请前两件（故障隔离、告警联动）；本件作为备选，等有明确区别于现有技术的实现后再决定。
