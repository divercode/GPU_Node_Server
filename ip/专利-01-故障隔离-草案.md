# 发明专利申请草案

## 一种基于GPU硬件错误与作业映射的GPU节点故障隔离方法及系统

> 草案说明：本文件是技术交底书/权利要求草案，不是正式申请文件；申请前必须做专利检索，并由专利代理师根据真实实现和实验数据改写。文中“示例”不构成对现有技术的承认或对效果的保证。

## 一、技术领域

本发明涉及 GPU 集群运维与作业调度技术领域，尤其涉及一种基于 GPU 硬件错误与作业映射的 GPU 节点故障隔离方法及系统。

## 二、背景技术

GPU 集群中，GPU 可能发生 XID 错误、不可纠正 ECC、温度过高、功耗异常、NVLink CRC 增长等硬件异常。现有做法通常由 DCGM/Prometheus 产生告警，再由运维人员手工判断影响范围并执行节点 drain；也有系统在检测到节点故障后自动 drain 整个节点。

现有方案存在以下问题：

1. 监控告警与 Slurm 作业分配信息分离，难以确定异常 GPU 上具体运行了哪些作业；
2. 只要单卡异常就 drain 整个节点，影响同节点其他健康 GPU 上的作业，造成资源浪费；
3. 作业与 GPU 的映射可能缺失或过期，直接自动 drain 容易误伤；
4. 缺少“检测—影响面计算—分级隔离—恢复验证”的闭环，隔离后何时恢复缺少依据；
5. 缺少幂等、限速和审计，自动处置可能重复执行或扩大影响。

## 三、发明内容

### 3.1 要解决的技术问题

本发明要解决的技术问题是：在 GPU 级硬件异常发生时，如何利用 GPU 与作业的双源映射和映射置信度，确定最小隔离范围，并在保证安全的前提下自动执行可恢复、可审计的隔离动作。

### 3.2 技术方案

一种基于 GPU 硬件错误与作业映射的 GPU 节点故障隔离方法，包括：

**S1、采集 GPU 级遥测数据。**  
按 GPU 唯一标识（UUID）采集节点名、GPU 索引、温度、功耗、利用率、显存、XID 错误码、ECC 计数、NVLink CRC/重放计数等指标；采集周期可配置，例如 15 秒。

**S2、构建 GPU—作业映射并计算映射置信度。**  
从至少两个来源获取映射：

- 来源 A：作业 Prolog 在 GPU 节点写入的映射文件，文件名包含 GPU 标识，内容包含 JobID；
- 来源 B：调度器查询结果，包括作业分配记录中的节点、GPU 列表和 JobID。

当来源 A 与来源 B 对同一 GPU 给出相同 JobID 时，映射置信度为高；仅一个来源存在时，为中等；两个来源均缺失或冲突时，为低。

**S3、生成故障事件。**  
对 S1 的指标按规则进行多周期确认：致命 XID、不可纠正 ECC 等可单周期触发；温度、功耗、NVLink CRC 等需连续 N 个采集周期满足阈值才触发；对同一 GPU 的重复告警进行去重和合并，生成包含 GPU、节点、故障类型、严重级别、时间窗口和映射置信度的故障事件。

**S4、计算影响面并确定隔离范围。**  
根据故障事件的 GPU 标识和 S2 的映射，确定受影响的 JobID、用户、账号和节点；根据故障级别和映射置信度确定隔离范围：

- 高置信度 + 致命故障：将该 GPU 标记为隔离，并在满足条件时对该 GPU 所在节点执行 drain；若节点上存在无法迁移的关键作业，则先通知并等待策略允许；
- 高置信度 + 非致命故障：仅隔离异常 GPU 或降低其调度权重，不立即 drain 整个节点；
- 中/低置信度：仅生成告警和工单，不执行自动 drain，等待人工确认或补全映射。

**S5、执行隔离动作。**  
生成隔离描述符，包含节点、GPU、JobID、原因、严重级别、有效期和操作来源；通过调度器接口执行节点 drain/恢复、通过 GPU 黑名单或 Prolog 过滤阻止异常 GPU 被新作业使用；对同一故障事件使用幂等键，限制单位时间内自动动作次数，并记录操作人、前后值、来源和 request_id。

**S6、恢复验证与闭环。**  
隔离后执行恢复检查：GPU 自检/诊断、驱动状态、XID/ECC 计数是否清零或稳定、温度/功耗是否恢复；连续 M 个采集周期满足健康条件后，清除隔离描述符并恢复调度；若不满足，保持隔离并升级告警。全过程写入审计。

### 3.3 有益效果

- 将 GPU 级异常与具体作业关联，避免“只报 GPU 故障、不知道影响哪个作业”；
- 通过双源映射和置信度，降低映射过期导致的误隔离；
- 对非致命故障优先做 GPU 级隔离，减少整节点 drain 对健康 GPU 的影响；
- 通过多周期确认、幂等、限速和恢复验证，提高自动处置的安全性和可审计性；
- 可与 Slurm、DCGM、Prometheus、Alertmanager 等现有组件配合，不需要替换调度器。

## 五、具体实施方式

### 5.1 示例环境

示例集群包括 2 台 GPU 服务器，每台 8 张 A100 80G，共 16 卡；调度器为 Slurm；监控为 DCGM exporter + Prometheus；采集周期 15 秒。

### 5.2 映射示例

作业 `200101` 被分配到 `gpu-01` 的 GPU 0–3。Prolog 在 `gpu-01` 的映射目录写入 4 个文件，文件名分别为对应 GPU UUID，内容为 `200101`；同时后端从 Slurm 查询到作业 `200101` 的分配节点和 GPU 列表。两边一致，因此这 4 张卡的映射置信度为高。

### 5.3 故障处置示例

`gpu-02` 的 GPU 0 连续 2 个周期上报 XID 79。S3 生成“致命 XID”故障事件，S2 得到该卡映射到作业 `200103` 的高置信度映射。S4 计算影响面：作业 `200103`、其用户/账号、节点 `gpu-02`；S5 生成隔离描述符，调用调度器将 `gpu-02` 置为 drain，并在 Prolog/GPU 黑名单中阻止 GPU 0 被新作业使用，同时通知作业负责人并创建工单。S6 在更换/复位后连续 6 个周期验证通过，清除隔离描述符并恢复节点。

### 5.4 低置信度示例

`gpu-01` 的 GPU 5 温度超过阈值，但映射目录中缺少该卡文件，Slurm 查询也只返回节点级分配。S2 判定置信度为低；S3 仍生成告警；S4/S5 只通知运维并请求补全映射，不自动 drain。这样避免误隔离正常作业。

### 5.5 非致命故障示例

某 GPU 的 NVLink CRC 在 30 分钟内增长超过阈值，但作业仍可运行。S5 仅把该 GPU 标记为“降权/禁排”，不 drain 整个节点；后续作业不再分配到该卡，已有作业继续运行并由用户决定是否迁移。

## 六、权利要求书（草案）

**1.** 一种基于 GPU 硬件错误与作业映射的 GPU 节点故障隔离方法，其特征在于，包括：

S1、按 GPU 唯一标识采集 GPU 级遥测数据，所述遥测数据至少包括节点名、GPU 索引、温度、功耗、利用率和硬件错误计数；

S2、基于 Prolog 映射文件与调度器分配记录构建 GPU—作业映射，并根据两个来源的一致性计算映射置信度；

S3、根据所述遥测数据按故障类型和多周期阈值生成故障事件，所述故障事件包括 GPU 标识、节点、故障类型、严重级别、时间窗口和映射置信度；

S4、根据所述故障事件和所述映射置信度确定受影响作业和隔离范围；

S5、生成隔离描述符并执行隔离动作，其中高置信度的致命故障触发节点 drain 和异常 GPU 禁排，高置信度的非致命故障触发 GPU 级禁排，中/低置信度故障仅生成告警和人工处置任务；

S6、对隔离对象执行恢复验证，连续满足健康条件后清除隔离并恢复调度。

**2.** 根据权利要求 1 所述的方法，其特征在于，S2 中，当所述映射文件与所述调度器分配记录对同一 GPU 给出相同 JobID 时判定为高置信度；仅一个来源存在时判定为中等置信度；两个来源均缺失或冲突时判定为低置信度。

**3.** 根据权利要求 1 所述的方法，其特征在于，S3 中，XID 致命错误和不可纠正 ECC 采用单周期触发，温度、功耗和 NVLink CRC 采用连续 N 个采集周期触发，N 为大于 1 的整数。

**5.** 根据权利要求 1 所述的方法，其特征在于，S5 中，所述隔离描述符包括节点、GPU、JobID、故障原因、严重级别、有效期、操作来源和幂等键；对同一故障事件重复执行隔离动作时，根据所述幂等键去重。

**6.** 根据权利要求 1 所述的方法，其特征在于，S5 中，对单位时间内的自动隔离动作进行限速，超过限速阈值时转为人工审批。

**7.** 根据权利要求 1 所述的方法，其特征在于，S6 中，所述恢复验证包括 GPU 自检、驱动状态、XID/ECC 计数、温度和功耗中的至少两项，并在连续 M 个采集周期满足条件后恢复。

**8.** 根据权利要求 1 所述的方法，其特征在于，S4 中，根据异常 GPU 关联的作业、用户、账号和节点计算影响面，并按照影响面生成通知范围和工单优先级。

## 七、摘要

本发明公开一种基于 GPU 硬件错误与作业映射的 GPU 节点故障隔离方法及系统。该方法按 GPU 唯一标识采集遥测数据，利用 Prolog 映射文件和调度器分配记录构建 GPU—作业双源映射并计算置信度；按故障类型和多周期阈值生成故障事件；根据故障级别和映射置信度确定受影响作业与最小隔离范围；对高置信度致命故障执行节点 drain 和 GPU 禁排，对非致命故障执行 GPU 级禁排，对低置信度故障仅告警；隔离后执行恢复验证并清除隔离。该方法可降低误隔离和整节点 drain 的影响，提高 GPU 集群故障处置的安全性和可审计性。
